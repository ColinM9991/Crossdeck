Theme Colourblind

Colourblind modes

Four repalette modes for the known colour-vision deficiencies. Each mode is a layer on top of the active theme that remaps the four semantic roles (accent, ok, warn, info) to hues that stay distinguishable under that deficiency.

How it works

A mode is a single attribute, html[data-cb="..."], layered over data-theme. Only 14 tokens change per mode: the three variants of each role (--role, --role-line, --role-bg) plus --selected-bg and --on-accent, which are derived from the accent. Surfaces, text and line tokens keep the theme's values, so the layout is untouched. Because the layers only ever redefine token keys, the combination every theme × every mode is valid by construction.

The modes split into two surface classes in the selectors. The dark class (the :not([data-theme="light"]):not([data-theme="sepia"]) selector) covers dark and dusk; the light class selector covers light and sepia. Dusk therefore uses the same colourblind values as dark. Each mode below gives both.

The four modes

Deuteranopia and protanopia (one shared selector group, identical values)

The red-green axis is broken. The system moves to the Okabe-Ito colour-blind-safe set: a blue accent, a blue-green ok, an orange warn, and a reddish-purple info. The light class uses darker variants of the same hues to hold contrast on white and cream.

Achromatopsia

No hue perception. Roles stop differing in hue and instead form a lightness ladder: on dark surfaces the ladder runs from near-white warn down through light greys; on light surfaces it is the inverse, from near-black warn up through mid greys. The system's non-colour channels (text labels, icons, shapes) do the identifying work here.

Contrast guarantee

Every role-on-surface pair in every mode clears 4.5:1 on the worst surface of its theme class and on the role's own tint. The prototype verifies this programmatically before release, so the values above are not approximations.

How the setting is exposed and stored

AspectBehaviour
UIThe settings page, Appearance card: a select.input with Off, Deuteranopia, Protanopia, Tritanopia, Achromatopsia, bound to CrossdeckCB.set and initialised from CrossdeckCB.get(). The help text reads: "Repalettes the interface's status colours to hues that stay distinguishable under the chosen colour-vision deficiency. Layers on top of the theme."
PersistStored under its own key, localStorage["crossdeck-cb-mode"], independent of the theme. set('') clears the mode.
First paintApplied by theme.js before the body renders, alongside the theme.
Live syncSame storage-event mechanism as the theme: all open pages switch together, and in-prototype links carry ?cb= for origins that cannot share storage.
CompositionMode and theme are independent axes. The 14-token remap applies on top of whatever theme is active; there is no per-theme mode state to desynchronise.

Guidance

  • Colourblind modes are a second layer, not the primary channel. Status in this system is never colour alone: pills carry a text label, notes carry an icon, and the warn role is reserved for things a user must act on. The modes make the colour channel itself safe for the four deficiencies.
  • When porting to Avalonia, keep the 14 remapped keys as one small override dictionary per mode. Merging it after the theme dictionary reproduces the layering exactly, and "off" simply means not merging it.
  • Do not add per-component colourblind special cases: if a component reads the role tokens, it is already correct under every mode.
