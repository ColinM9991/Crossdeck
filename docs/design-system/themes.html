Themes

Four themes: dark (default), light, sepia and dusk. A theme is a re-tuning of the tokens, not a different component set: 37 of the 39 tokens are overridden per theme (the two font stacks stay shared).

How a theme is applied

A theme is a single attribute on the document element, html[data-theme="..."]. Omitting the attribute is the dark theme. theme.js owns the whole cycle:

StepWhat happens
PersistThe chosen theme is stored in localStorage["crossdeck-theme"]. Unknown or stale stored values fall back to the default rather than erroring.
First painttheme.js loads in <head> and applies the stored value before the body renders, so there is no theme flash.
SwitchCrossdeckTheme.set(value) validates against the four known themes, sets or removes the data-theme attribute (dark removes it), persists, and rewrites the in-prototype links. CrossdeckTheme.get() returns the current value or null.
Live syncSame-origin tabs hear the storage event and re-apply, so every open page switches together. The storage event also fires with a null key, which theme.js treats as "re-read both keys".
Fallback for split originsBrowsers that give each file:// page a unique origin (Firefox) cannot share storage: the theme and the colourblind mode also ride on the ?theme= and ?cb= URL parameters of in-prototype links, and the set methods keep those links current. A URL parameter also wins over storage when present, and is persisted on the way in.

The user-facing switch lives on the settings page, Appearance card: a select.input bound to CrossdeckTheme.set, initialised from CrossdeckTheme.get(). A second select on the same card drives CrossdeckCB.

The four themes

Dark (default, no attribute)

Near-black surfaces (#0e1116) with a one-step card lift. The only theme that uses inset top highlights (1px white at 2-3%) on its shadows for the raised edge, and the only one whose top bar has no shadow at all (--chrome-shadow: none). The accent is the brightest in the set: cyan #41d9f0 at 10.3:1 for the focus ring.

Dusk

A mid slate-blue between dark and light: surfaces are a visible step up from dark's near-black (#1d2536) so the page reads as a night scene rather than a void, and the text is soft (#dbe3f2) rather than white. The only theme with its own chevron stroke: the shared #6b7484 measures 2.8:1 on dusk's card, under the 3:1 standard for UI components, so the token is re-tinted to #8fa0c0.

Contrast notes carried in the stylesheet

  • Tertiary text was lightened in v5 specifically to clear WCAG AA: v4's #6b7484 measured 3.70:1 on cards, under the 4.5:1 standard for normal text.
  • The editor page's kind pill uses --chip-text rather than --text-3 because dusk's #8b98b3 on dusk --chip-bg measures 4.14:1, still under 4.5:1.
  • Every colourblind mode's role-on-surface pairs clear 4.5:1 on the worst surface of their theme class; on the role's own tint all pairs clear 4.5:1 except two marginal sepia cases (tritanopia green 4.26:1, achromatopsia violet 4.32:1, both above 3:1). docs/tools/contrast-check.ps1 re-verifies these numbers from the CSS values (pwsh docs/tools/contrast-check.ps1 from the repo root), so the numbers are checked, not assumed.

Building the theme in Avalonia

Everything below is what a manual Avalonia implementation needs: the resource keys, the base dictionary values, the merge order for the four themes and the four colourblind overrides, and the value-type notes. The per-theme values (37 keys each) are the master table on the tokens page; the 14-key colourblind overrides are on the colourblind page. Both tables are audited verbatim against design-system.css.

Type notes: rgba(r, g, b, a) converts to an ARGB Color with the alpha byte round(a × 255) (e.g. rgba(65, 217, 240, 0.45) is #7341D9F0). Shadows have no 1:1 Avalonia property: model each as a DropShadowEffect from the main blur layer (offset, blur and opacity) and drop the 1px inset top highlight, or accept a slightly flatter look. The chevron is an 11px vector (the --chevron data URI is the path); its stroke colour is per theme, so it is a resource, not a constant.

Override dictionaries and merge order

  • Base (dark), 39 keys (the values above). Always present.
  • Theme override, 37 keys each (light, sepia, dusk): the per-theme columns of the tokens master table. Merged over the base when that theme is active. "Dark" is the absence of a theme override.
  • Colourblind override, 14 keys: the four mode tables on the colourblind page. Each mode has two key sets: a dark-class set (applies under dark and dusk) and a light-class set (applies under light and sepia). Merged last, after the theme override; "off" is the absence of the merge. Only 14 keys are redefined, so every other key keeps the theme's value and there is no per-theme mode state to desynchronise.
  • Implementation. A theme service holds the four theme dictionaries and the four colourblind dictionary pairs; on change it (re)merges base + active theme + active mode onto Application.Current.Resources (a MergedDictionary), persists the choice (mirroring CrossdeckTheme / CrossdeckCB's get/set/persist/sync contract), and the dictionaries themselves are data, so the same values work for XAML controls and for code that reads resources.
  • Avalonia's ThemeVariant covers the dark/light pair only (Fluent themes flip on it); sepia and dusk are runtime-swappable dictionaries as above. Verify the current Avalonia theme-variant resource syntax in the docs before relying on it; the 11-era patterns have drifted.

Contrast verification

docs/tools/contrast-check.ps1 reads the token values straight out of design-system.css and asserts the guarantees this page and the colourblind page make: every mode's four role solids clear 4.5:1 on the worst surface of their theme class and on the role's own tint, Text3 on Card clears 4.5:1 in all four themes, the focus ring clears 3:1, and the dusk chevron re-tint and the kind-chip ChipText swap hold. Run it after changing any value; it fails before the port would.
