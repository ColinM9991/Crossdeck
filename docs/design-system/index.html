Overview

The Crossdeck UI design system, documented from the live HTML prototype. Single source of truth for the Avalonia implementation in src/Crossdeck.UI.

What this is

Crossdeck's interface follows a small, calm visual language: dark surfaces by default, one cyan accent, a four-role status palette (accent, ok, warn, info), 13px Inter-class type, and component primitives that repeat across every page. The prototype at docs/ui-prototype/ is the reference build; this site documents its tokens, themes, colourblind modes and components so the Avalonia app can be built without re-deriving decisions.

Everything on these pages is sourced from the prototype's design-system.css (tokens and component rules), theme.js (theme and colourblind switching) and the six page files. Values are quoted verbatim; where the CSS carries a rationale (contrast fixes, reflow behaviour), the note is included.

How the layering works

Colours are not hard-coded in components. Every component reads from design tokens, and the tokens are layered:

  1. Base (dark, default). The :root block defines all 39 tokens. No data-theme attribute means dark.
  2. Theme override. html[data-theme="light" | "sepia" | "dusk"] re-tunes 36 of the 39 (fonts stay shared). The override is applied by theme.js before first paint, from the value stored in localStorage["crossdeck-theme"].
  3. Colourblind repalette. html[data-cb="deuteranopia" | "protanopia" | "tritanopia" | "achromatopsia"] layers on top of the active theme and remaps the 14 semantic-role tokens (the accent/ok/warn/info families, plus --selected-bg and --on-accent). It is an independent setting: its own storage key, its own URL parameter, and it composes with any theme.

Because both layers only ever redefine tokens, a component written once against token names is correct in all 4 themes and all 4 colourblind modes with no changes. That is the contract the Avalonia resource dictionaries must preserve: base dictionary, theme override dictionaries, colourblind override dictionaries, and component styles that only reference token keys.

Design rules the system enforces

These are stated in the prototype's stylesheet and hold across all pages:

  • Contrast. Body text on its surfaces meets WCAG AA (4.5:1 for normal text). The v4 tertiary text colour measured 3.70:1 on cards and was lightened to #828c9e to pass.
  • One focus ring. Every control shows the same :focus-visible ring: 2px --cyan, 2px offset. Cyan on the dark theme measures 10.3:1 against adjacent surfaces.
  • Motion is essential-only. All non-essential animation and transition stops under prefers-reduced-motion.
  • Actions are buttons. Anything that acts is a <button>; dead <a href="#"> anchors do not exist. Navigation stays <a href>.
  • Fluid layout. No fixed canvas: three states, desktop grid, stacked columns at 1180px, and a bottom nav rail at 640px. Interactive targets grow to 44px on the smallest layout.
  • Status is never colour alone. Pills and notes pair a colour role with a text label or an icon, so the colourblind repalettes are a belt-and-braces layer rather than the only channel.

Notes for the Avalonia port

Direction of travel, not prototype fact. The prototype's layering maps cleanly onto resource dictionaries:

  • Tokens.axaml holds the dark base set; Tokens.Light.axaml (and sepia/dusk equivalents) redefine the same keys, so a dictionary merged later wins per-key.
  • Colourblind modes are a second override axis: four more small dictionaries that redefine only the 14 role keys, merged after the theme dictionary when a mode is active.
  • Component styles reference token keys only, never raw colours, so they stay valid under every combination.
  • Avalonia's ThemeVariant covers the dark/light axis; sepia and dusk, and the colourblind overlay, need their own dictionaries (or a runtime merge), because there is no built-in third variant. Verify the 12.x theme-variant resource syntax in the Avalonia docs before relying on it.
